# Work Order Template

## Purpose

A work order is a self-contained markdown file generated by the executor for a single task. It contains everything a worker needs to implement that task and nothing else. No DAG structure, no other tasks, no system state.

Workers receive only their work order. They implement it, report done or stuck. Fully portable across harnesses, models, machines, and time.

## Why self-contained

- **Portable**: any AI, any harness, any machine, any time
- **Debuggable**: if output is wrong, inspect exactly what the worker was given
- **Archivable**: permanent record of what was requested and how
- **Cacheable**: identical contracts produce identical work orders; fulfilled work orders feed the replay cache
- **Minimal context**: worker loads only what it needs; no context window waste

## Work order schema

```markdown
# Work Order: {task_id}

## Contract Hash
`{hash}` — check contract archive before implementing. If a verified fulfillment exists for this hash, run it against the fixtures below. If fixtures pass, skip implementation entirely.

## Task
**ID**: {task_id}
**Name**: {task_name}
**Description**: {task_description}

## Acceptance Criteria
{list of criteria, each testable}

## Mode
{spec-only | validated | enforced}
{one-line explanation of what this means for this task}

## Provides Contracts
{for each contract this task must satisfy:}

### {contract_id}
**Type**: {interface | schema | behavioral}
**Signature**:
```{language}
{signature}
```
**Invariants**:
{list}
**Side Effects**:
{list, or "none"}
**Fixtures**:
{for each fixture:}
- **{label}**: input: {input} → expected: {expected_output_or_error}

## Requires Contracts
{for each upstream contract this task depends on:}

### {contract_id}
**Provider**: {provider_task_id}
**Status**: {complete (real implementation) | building (stub available)}
**Path**: {real implementation path, or stub path}
**Signature**:
```{language}
{signature}
```

## Semantic Conventions
{Every convention from metadata.conventions whose applies_to matches this task or "*". These are authoritative interpretations — do not guess or substitute your own. Example: "Magnetic polarity: north = positive throughout this system."}
{If none apply: "No project-wide conventions apply to this task." — state this explicitly so the worker knows the absence is deliberate, not an omission.}
{Where a convention above and a contract in this order disagree, the contract governs — and the disagreement is a defect in one of them, so report `stuck` rather than resolving it yourself. See `contracts.md` → Conventions vs contracts.}

## Testing Requirements
**Test artifact path**: `{test_artifact_path}` — allocated by the executor. Write your test suite here.

Tests are part of this task, not a follow-up. The task is not done until its tests pass.

Test scope: assert over this task's own artifacts. Do not scan directories that other tasks will write into — a test that asserts an exact manifest of a shared directory fails the moment any later task adds a file. Where this task owns a repo-wide invariant (e.g., a layout contract), assert the invariant (superset, boundary) rather than a snapshot of current contents.

- Include the contract fixtures above in the test suite — they are the floor, not the ceiling
- Beyond fixtures, write unit tests verifying internal correctness: state transitions, side effects, sub-component interactions, and semantic alignment with the conventions above
- Prefer tests that set up a realistic condition with exactly one provably correct outcome, such that any deviation — from any failure mode, anticipated or not — registers as a failure. One correct alignment state, infinite detectable wrongs.
- Avoid tests that only check whether one specific thing went wrong one specific way

## Write Safety (include when the task modifies existing files or produces large outputs)
{Conditional section — the executor includes this when the task involves large writes or edits to files that already exist.}

- **Atomic writes for existing files**: write to a temp path, then swap (rename/hardlink) over the original, then clean up. An interrupted mid-write must never leave the original file nuked.
- If write+swap+cleanup fits in a **single tool call** in your environment, there's no tradeoff — use atomic writes universally.
- If atomic writes require **separate tool calls**, use them strategically: every tool call re-sends your full context window, so a separate swap call roughly doubles the token cost of the write. Weigh your current token/quota/context situation before choosing.
- For **very large writes** where quota or tokens could run out mid-operation: chunk the write into several smaller appends/parts so an interruption loses one part, not the whole operation.

## Wash (include only when the worker wash is enabled for this task)
{Conditional section — the executor includes this when `wash.worker` is true, or
when this task appears in `wash.per_task_overrides`. Omit it entirely otherwise;
a work order that mentions washing without enabling it teaches workers to skim
the section.}

Passing tests does not mean you are finished — it means nothing you thought to
check is broken. Before you report anything, run the wash prompt from `wash.md`
and look for what you missed.

Read the prompt, let the generation run, then categorize your findings:

- **A — stuff you actually found.** Real things only; inventing findings just
  sends you chasing ghosts. But *unsure* is not the same as *made up*: if you
  cannot tell whether something counts, put it in C. Never drop it on the floor.
- **B — stuff you looked at and ruled out.** An actual decision — you will not
  chase it twice.
- **C — stuff you could not settle**, and anything else worth recording. Open
  questions go here, not in B: B says "I decided no", C says "somebody should
  look at this properly".

Stick to your own patch. You cannot see the rest of the project, so nothing out
there can be an A of yours. A hunch that genuinely worries you is a C.


## Chunk Context
**Chunk**: {chunk_id} ({chunk_name})
**Boundary contracts this chunk exposes**: {list of contract_ids}
**Cross-chunk stubs consumed**: {list with paths, or "none"}

## Warm Start (if available)
{If a near-match was found in the contract archive:}
**Previous fulfillment**: {path or reference}
**Delta from current contract**: {what changed — different invariants, additional fixtures, etc.}
**Suggestion**: patch the previous implementation to satisfy the updated contract rather than rebuilding from scratch.
```

## Generation process

The executor generates work orders by:

1. Querying task details via CLI: `taskdagger-cli.py task {task_id}`
2. Querying provides/requires contracts: `taskdagger-cli.py task-contracts {task_id}`
3. Querying stub paths: `taskdagger-cli.py task-stubs {task_id}`
4. Selecting applicable conventions from `metadata.conventions` (matching `applies_to`) and rendering the Semantic Conventions section
4a. Allocating the test artifact path from the same namespace as the task's other artifacts; a task required to deliver tests with no allocated test path is malformed
5. Including the Write Safety section when the task's outputs modify existing files or are large enough that interruption mid-write is plausible
6. Computing contract hash: hash(signature + invariants + fixtures + side_effects) for each provides-contract
7. Checking contract archive for hash matches (replay check)
8. If replay hit with passing fixtures → skip implementation; the replayed artifact still enters chunk verification and integration testing like any freshly built one (see caution below)
9. If near-match → include warm start section
10. If no match → generate standard work order
11. Including the Wash section only when `wash.worker` is enabled or the task is listed in `wash.per_task_overrides` — include the wash prompt from `wash.md` in the section so the worker has it without needing to load the skill

12. Writing the .md file to the work orders directory

When a work order names files for the worker to read, say how to read them — see `executor.md` → Orchestration discipline. A bare list of paths produces one tool call per path.

## Replay caution

A hash match proves interface equivalence, not semantic equivalence. The hash covers signature + invariants + fixtures + side_effects — it does not cover project conventions. An archived implementation may have been built under a different convention regime (opposite sign convention, different index base) and still pass a finite fixture set. Therefore:

- Replay never bypasses chunk verification or integration testing
- When a replay candidate's origin project declared different conventions (or none), treat it as a warm start, not a hit
- Fixtures that pin down convention-sensitive behavior (e.g., a fixture whose expected output is only correct under the declared polarity) make the hash itself convention-aware — prefer writing fixtures this way during contract compilation

## Worker protocol

The worker's job is simple:

1. Read the work order
2. Check contract hash against any local cache (optional, if worker has one)
3. Implement, honoring the semantic conventions section
4. Write unit tests per the testing requirements; include contract fixtures in the suite
5. Task is done only when the full test suite passes (fixtures + unit tests)
6. If mode is `enforced`: include test results in the completion report
7. If the order has a Wash section, wash before reporting — run the prompt and
   categorize findings. If there is no Wash section, skip this step; its absence
   is deliberate.

8. Report completion: "done" with a summary of what was built and test results, or "stuck" with what's blocking

A `stuck` report is washed too. It spends executor attention, so it should be the
real list rather than the first blocker you hit.

The worker does not need to understand DAGs, chunks, executors, or phases. It just implements the contracts in its work order.

## Test-authoring brief (adversarial verification)

When the executor dispatches a task with adversarial verification (see `executor.md` → Adversarial verification), the work order splits into two:

1. **Implementation brief** — the standard work order above, minus the Testing Requirements section
2. **Test-authoring brief** — contains the contract (signatures, invariants, fixtures), acceptance criteria, semantic conventions, and the Testing Requirements section. It does **not** contain the implementation, the implementation artifacts, or any reference to what the implementer built.

The test author writes a suite that verifies the contract from the outside — the same surface a consumer would see. They never see the implementation. The executor runs both suites (worker's and test author's) and reports the intersection.

## Drone-piloted task

When the executor dispatches a task for drone execution (see `drone_execution.md`), the work order carries additional fields:

```markdown
## Drone Execution
**Provider**: {provider name from manifest}
**Timeout**: {per-call timeout in seconds}
**Max rounds**: {retry bound}
```

The pilot sends the drone the contract, fixtures, and acceptance criteria via the API using heredoc request bodies — never shell-inlined. The pilot writes the test suite itself against the contract, never showing it to the drone. Report `mode: drone` and round-trip count in the completion summary.

## Storage convention

```
.taskdagger/work-orders/
├── {task_id}.md              # the work order
├── {task_id}.result.md       # worker's completion report (optional)
└── {task_id}.artifacts/      # implementation artifacts (if applicable)
```

## Contract archive integration

After a task is verified, the executor stores the fulfilled contract:

```
.taskdagger/contract-archive/
└── {contract_hash}/
    ├── contract.json         # the contract definition
    ├── work_order.md         # the work order that produced it
    └── implementation_ref    # pointer to the implementation artifacts
```

Future work orders with the same hash check here first. Cross-project archives follow the same structure at a shared location.
