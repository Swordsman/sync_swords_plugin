# Procedures

All of these assume the user has said yes, and each step stays within what they approved (see SKILL.md, rule zero). Reading their memory to plan changes is itself a step that needs approval.

## The standing self-check

Put this in the always-loaded file, and ask it whenever a task starts or shifts:

> Am I forgetting to load or consider a skill or memory that's indicated right now? Is there anything important, concerning, paradoxical or easy to miss that we might be overlooking, in context or anywhere else?

## Classifying a line

For each line of memory, ask: does this need to hold every turn, whatever the task?

- **Yes:** it goes in the always-loaded file, or in a `!!` file.
- **Only in certain situations:** it goes in a conditional file whose description names that situation. Add a `?!` pointer if the situation is high-value or easy to miss.
- **About one project:** it goes in that project's file.
- **Not worth keeping:** leave it out.

A file that mixes always-on and conditional lines either gets `!!`, or gets split.

## Making a new file

1. **Name it** by its subject.
2. **Write the description as a trigger** (see syntax.md), condition first.
3. **Add keywords** if it's a project or area.
4. **Add a pointer** in the always-loaded file if its trigger is high-value or easy to miss.
5. **For a project, create the file when the project starts,** not after.

## The full sweep (first adoption, or a periodic tidy)

1. **Batch-read the files,** several per read call, so the pass doesn't cost one call per file. Read them all; a file judged by its description alone can hide an always-on line.
2. **Classify every line** as above.
3. **Move always-on lines** into the always-loaded file or a `!!` file.
4. **Rewrite every description** as a trigger.
5. **Add pointers** for the high-value triggers.
6. **Report** what moved and why, and anything you weren't sure about.

Show the planned changes and get a yes before the sweep writes anything, and keep the originals.

## When the always-loaded file nears its cap

Find its broadest categories of conditional content, move each into its own file with a trigger description, and leave a pointer behind. The routing-file pattern helps: one file for "how to choose X" can point to a file for each X.

## The session index

Keep one file listing sessions where real progress or brainstorming happened: the date, a link or id, and the specific topics in concrete words. Add the entry while the session is still running, since sessions can end without warning. To revisit a session, search within it or read only the relevant slice; never load a whole transcript.

## Persist or lose

When something worth keeping comes up (a decision, a user's stated preference, a design, a lesson), write it down then, in memory, a repo or a document. Not at the end of the session.

## Always

- **The harness's own memory rules come first:** privacy, what may be stored, required tags.
- **Files about other people** load only when the user brings that person up; never mark them `!!`.
- **A user's existing conventions win over this system.**
